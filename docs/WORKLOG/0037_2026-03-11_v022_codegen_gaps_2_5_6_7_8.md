### Gap 5 — 0x022E oscillation (CONFIRMED CORRECT)

**Problem**: `0x022E` (PACKET_ZC_PROPERTY_HOMUN) shows `77→73→77` in `lengths_map.go`.

**Investigation**: Ran `ExtractStructs` on `packets_struct.hpp` at the three breakpoints:

| PACKETVER | Bytes | Explanation |
|-----------|-------|-------------|
| 20181121 | 77 | `itemId` = `uint32` (4 bytes); sp/maxSp = `uint16` |
| 20190619 | **73** | New struct variant assigned to `0x022e`; `itemId` field absent (moved to `0x0b2f`) |
| 20191120 | 73 | Still 73 |
| 20200916 | 77 | `sp`/`maxSp` promoted to `uint32` → back to 77 |

**Conclusion**: Not a bug. The 73-byte drop reflects a genuine structural change:
rAthena introduced `PACKET_ZC_PROPERTY_HOMUN3` (mapped to `0x0b2f`) and assigned the
old `0x022e` ID to a new struct that no longer carries `itemId`. The oscillation is
correctly produced by the preprocessor.

### Gap 7 — `quest_update_mission_hunt` (CONFIRMED INTENTIONAL SKIP)

**Verification**: The action has no implementations because:
1. `0x02B3` was removed in worklog 0012 (legacy/deprecated, no function sends it)
2. `0x09FA` (ZC_UPDATE_MISSION_HUNT_EX) is variable-length (`-1`) and already in
   `lengths_map.go` via clif_packetdb Part 1. The struct is `packet_quest_update_header`
   — an old-style lowercase struct, not `PACKET_ZC_*`, so it doesn't fit the decode
   codegen pattern.

The framing engine correctly handles `0x09FA` (won't desync). The decode simply doesn't
emit an event for this packet — acceptable for Phase 7.
