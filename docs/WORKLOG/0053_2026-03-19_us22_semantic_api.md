## Key Design Notes

### `s.core.packetver` Access

`Send` accesses `s.core.packetver` directly since `semantic.go` is in the same package as
`map.go`. No API surface change to `sessionCore` was needed.

### `s.Encode(&id)` Call

`Send` reads the packet ID bytes 0–1 back from the encoded buffer, calls `s.Encode(&id)`,
and writes the XOR-obfuscated ID back. This matches the existing `obfuscation.go` contract.
No `ShuffledCtoSID` is called — shuffle is the encode function's responsibility.

### sendRegistry Sizing

`sendRegistry` is `[maxSemanticAction + 1]SendEncoderFunc` — an array indexed by SemanticAction
value for O(1) lookup with zero allocation. `maxSemanticAction` is defined in the generated
`actions.go` as the highest assigned value (460 as of this run).

### 1 alloc/op in Benchmark (Expected)

The `BenchmarkRegisterAndFeed_SemanticHandler` shows exactly 1 alloc/op. This is expected:
the `receiveDispatch` lambda boxes the decoded event struct into `interface{}`, which cannot
be stack-allocated (escapes to heap). 0 allocs/op is NOT achievable with this design.

## Test Frame Sizes

A critical issue was discovered: the spec's suggested frame sizes (60 bytes for 0x007B) are
insufficient for the `ActorMoved_0x007B` decode function at `packetver >= 20181121`, which
reads up to `data[90:114]` (114 bytes minimum). All test frames were adjusted to 114 bytes
for the pv=20181121 test cases. This is consistent with the decode function's actual field
layout at modern packetvers.
