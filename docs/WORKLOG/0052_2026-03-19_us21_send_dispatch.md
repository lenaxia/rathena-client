## Key Design Decisions

### Filesystem-Based Function Existence Check

The original spec approach (using `resolveLayout` nil check to skip actions) was insufficient
because some hand-written encode functions (e.g. `EncodeDealFinalize`, `EncodePublicChat`) have
no struct layout in the VersionTable. These would incorrectly be treated as variable or skipped.

The solution: `GenerateRegisterFileWithDir` scans the `pkg/encode/` directory using `go/parser`
to find existing `Encode*` functions. Only actions with an existing encode function are included.
Additionally, the actual function signature (fixed `[N]byte` vs `[]byte`) is extracted from the
AST to determine whether `b[:]` wrapping is needed. This handles:

- `EncodeDealFinalize` (hand-written `[2]byte`, no VersionTable entry) → correctly emits `b[:]`
- `EncodePublicChat` (hand-written `[]byte`, no VersionTable entry) → correctly emits direct return
- `EncodeMoveTo` (generated `[5]byte`) → correctly emits `b[:]`

### VersionTable commonSize Fallback

For the unit tests (no encodeDir), the `GenerateRegisterFile` function uses the VersionTable
`commonSize` aggregation (matching `generateEncodeDispatcher` in encode.go). Nil layouts are
skipped (continue), not treated as variable. This is the same behavior as the encode generator.

### Actions Skipped

The following send-direction DB actions were NOT registered because they have no encode file:
- `enter_world` (PACKET_CZ_NOTIFY_ACTORINIT — no struct layout)
- `reply_party_invite` (PACKET_CZ_REPLY_JOIN_GROUP — no struct layout)
- `request_charlist` (PACKET_CH_ENTER_0x0065 — no struct layout)
- `game_login` (mixed: SYNTH_CH_ENTER_0x0065 has layout but is registered)

Wait — `game_login` IS in the register.go (checked `EncodeGameLogin` exists). The 5 skipped
from the encode codegen are a different set.
