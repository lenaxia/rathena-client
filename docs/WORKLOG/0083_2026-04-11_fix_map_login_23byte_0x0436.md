# Work Log 0083 — Fix 0x0436 map login: 23-byte packet for RE [20211103,20211118] and MAIN >= 20220330

**Date:** 2026-04-11
**Commit:** 12e23e6
**Release:** v0.6.3
**Type:** Bug fix — `pkg/session/fsm.go`, `pkg/encode/map_login.go`

---

## Problem

Bots connecting to a map server at `PACKETVER_RE_NUM >= 20211103` or
`PACKETVER_MAIN_NUM >= 20220330` were disconnected immediately on map entry.
No error was surfaced — the TCP connection was simply closed by rAthena.

---

## Root Cause

### rAthena ingress pipeline

`clif_parse` (`clif.cpp:25646`) reads `cmd = RFIFOW(fd, 0)`, optionally
XOR-decrypts it under `PACKET_OBFUSCATION`, looks up `packet_db[cmd]`, then
dispatches `packet_db[cmd].func(fd, sd)`. No further transformation occurs
between TCP read and handler call.

`clif_parse_WantToConnection_sub` (`clif.cpp:10625`) performs a strict length
check before doing anything:

```cpp
if( packet_len != packet_db[cmd].len )
    return 1;  // wrong length → set_eof(fd) → disconnect
```

`client_tick` (`pos[3]`, offset 14) is read from the packet at `clif.cpp:10660`
and immediately discarded — rAthena does not validate or use it.

### packet_db population — last write wins

`packetdb_readdb()` (`clif.cpp:25819`) includes `clif_packetdb.hpp` then
`clif_shuffle.hpp`. Both register via `packetdb_addpacket` which unconditionally
overwrites `packet_db[cmd].len` and `packet_db[cmd].func`. The final value for
any packet ID is the **last** `parseable_packet()` call in preprocessor order.

### The 23-byte condition

`clif_shuffle.hpp:4744`:

```cpp
#if PACKETVER_RE_NUM >= 20211103 || PACKETVER_MAIN_NUM >= 20220330
    parseable_packet( 0x0436, 23, clif_parse_WantToConnection, 2, 6, 10, 14, 22 );
#else
    parseable_packet( 0x0436, 19, clif_parse_WantToConnection, 2, 6, 10, 14, 18 );
#endif
```

`config/packets.hpp` line 22 defines when `PACKETVER_RE` (→ `PACKETVER_RE_NUM`)
is set:

```cpp
#if ( PACKETVER > 20151104 && PACKETVER < 20180704 ) \
 || ( PACKETVER >= 20200902 && PACKETVER <= 20211118 )
    #define PACKETVER_RE
#endif
#define PACKETVER_RE_NUM PACKETVER  // only when PACKETVER_RE is defined
```

For packetver outside the RE window, `PACKETVER_MAIN_NUM = PACKETVER`.

Intersecting these two definitions gives the exact Go condition:

| packetver range | rAthena registers | reason |
|---|---|---|
| `[20211103, 20211118]` | 23 bytes | RE window ∩ `PACKETVER_RE_NUM >= 20211103` |
| `>= 20220330` | 23 bytes | MAIN, `PACKETVER_MAIN_NUM >= 20220330` |
| everything else | 19 bytes | default |

### 23-byte field layout

```
clif_shuffle.hpp:4745
parseable_packet( 0x0436, 23, clif_parse_WantToConnection, 2, 6, 10, 14, 22 )

offset  0-1:  packet ID    0x0436
offset  2-5:  AID          pos[0]=2
offset  6-9:  GID          pos[1]=6
offset 10-13: AuthCode     pos[2]=10
offset 14-17: clientTime   pos[3]=14  (rAthena reads and discards)
offset 18-21: tick         (extra field absent from 19-byte variant; send 0)
offset 22:    sex          pos[4]=22
```

Cross-referenced against OpenKore `RagexeRE_2021_11_03.pm`:
```perl
'0436' => ['map_login', 'a4 a4 a4 V2 C', [qw(accountID charID sessionID unknown tick sex)]]
# pack: 2(id) + 4+4+4+4+4+1 = 23 bytes; sex at offset 22
```

### What was wrong

Both `fsmEncodeMapLogin` (`pkg/session/fsm.go`) and `EncodeMapLogin`
(`pkg/encode/map_login.go`) always produced 19 bytes regardless of packetver.
For the affected packetvers rAthena's length check (`packet_len != 23`) returned
error 1, triggering `set_eof(fd)` and closing the connection before any
authentication data was processed.

---

## Scope corrections vs work log 0888

Work log 0888 claimed `0x0437` (attack) and `0x0362` (pickup) are wrong for
RE=20211103. GCC preprocessing shows both are correct for RE and MAIN alike —
they are last-write-wins from `clif_shuffle.hpp:4749` and `:4732` respectively.
The bug was **only** the packet length of `0x0436`, not the packet IDs.

---

## Fix

### Condition

```go
(packetver >= 20211103 && packetver <= 20211118) || packetver >= 20220330
```

This directly mirrors `#if PACKETVER_RE_NUM >= 20211103 || PACKETVER_MAIN_NUM >= 20220330`
from `clif_shuffle.hpp:4744`, translated through `config/packets.hpp`'s RE window
definition.

### `pkg/session/fsm.go` — `fsmEncodeMapLogin`

Signature changed from `(aid, gid, authCode uint32, sex uint8) [19]byte` to
`(aid, gid, authCode uint32, sex uint8, packetver uint32) []byte`.

Returns 23 bytes (sex at offset 22) for the affected packetver windows;
returns 19 bytes (sex at offset 18) otherwise. Call site in `runMapPhase`
simplified from `enterArr := ...; enterPkt := enterArr[:]` to `enterPkt := ...`.

### `pkg/encode/map_login.go` — `EncodeMapLogin`

The original file was code-generated (`[19]byte`, `_ = packetver`). The codegen
dispatcher model uses `case packetver >= X` breakpoints and cannot express
non-contiguous closed intervals like `[20211103, 20211118]`. The file was
replaced with a manually-implemented version (same pattern as `actor_action.go`)
using the same condition as `fsmEncodeMapLogin`. The codegen preserves any file
whose header does not start with `// Code generated by internal/codegen. DO NOT EDIT.`
(`main.go:1436-1441`), so this file is safe from future codegen runs.

`pkg/encode/register.go` was regenerated automatically; the `b[:] ` no-op on the
old `[19]byte` return was collapsed to a direct `return EncodeMapLogin(r, pv), nil`.

### Why two copies instead of one

`pkg/session` cannot import `pkg/encode` — the cycle is in the other direction
(`pkg/encode` imports `pkg/session`). A shared helper package would be the clean
long-term solution but is out of scope here. The two copies are small, identical
in logic, and independently tested.

`clientTime` (`req.ClientTime`, offset 14): `EncodeMapLogin` propagates the
caller-supplied value; `fsmEncodeMapLogin` always sends 0. Both are correct —
rAthena reads `client_tick` at `clif.cpp:10660` and discards it immediately
(comment at `:10632`: `/* don't care about client_tick */`).

## Review process

Three rounds of adversarial review were run before the fix was considered complete:

**Round 1** caught: MAIN `>= 20220330` arm entirely missing from the condition.
Verified by GCC preprocessing with `PACKETVER_MAIN_NUM=20220330`.

**Round 2** caught: `EncodeMapLogin` (code-generated) always returned `[19]byte`,
making the registered `ActionMapLogin` encoder wrong for affected packetvers.
Fixed by converting to a manually-implemented file.

**Round 3** flagged: `EncodeMapLogin` propagates `req.ClientTime` while
`fsmEncodeMapLogin` sends 0. Verified in `clif.cpp:10632,10660` — rAthena reads
`client_tick` and discards it unconditionally. Not a bug.
